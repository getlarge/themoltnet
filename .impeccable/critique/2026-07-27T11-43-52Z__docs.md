## Design Specificity Verdict

**LLM assessment:** Partially product-specific. The dark homepage is recognizably MoltNet: teal network ring, amber identity core, near-black void, and exact operator language. The article surface remains category-interchangeable VitePress. Generic emoji feature icons, standard three-column chrome, and a globally expanded docs tree do not express the product’s strongest idea: independently verifiable identity, memory, and accountability.

**Deterministic scan:** The bundled detector returned exit code 0 with `[]`: zero findings, zero rule names, and zero file locations. This is a real clean scan, but it did not catch rendered issues. Browser inspection found mobile reflow failure, a missing home `main`, a heading-level jump, missing `aria-current`, small touch targets, and unconditional auth/interactive loading.

**Visual overlays:** No reliable user-visible overlay is available. The in-app browser was unavailable, so mutable injection could not be preflighted. Headless local Chrome provided the fallback visual and DOM evidence.

## Overall Impression

The docs are unusually trustworthy in voice and technically coherent, but their surface has not caught up with the product. The single biggest opportunity is to turn the canonical team-pilot journey into the organizing experience while fixing the custom header that currently breaks mobile navigation.

## What’s Working

1. **Precise, accountable voice.** Identity distinctions, spend-cap caveats, immutable-entry language, and operational warnings earn trust through specificity.
2. **Strong token and theme discipline.** Light and dark themes consistently use MoltNet tokens; sampled color pairs comfortably clear AA contrast.
3. **Useful expert affordances.** Local search, code groups, Quick Reference, and `llms.txt` create legitimate fast paths without weakening the prose.

## Priority Issues

### [P1] Mobile header breaks navigation and team-context access

- **Why it matters:** At 390px the document is 439px wide and the hamburger sits entirely offscreen at x=391–439. The custom “Select team” and “Log in” controls consume the missing width. After authentication, the actual team selector is hidden below 760px even though interactive examples instruct users to select a team in the navbar.
- **Fix:** Render one logged-out Log in action, move authenticated account/team selection into the mobile menu or a compact combined control, and keep the hamburger inside the viewport. Give touch controls a 44px hit area at touch breakpoints.
- **Evidence:** `docs/.vitepress/theme/index.ts`, `custom.css`, `components/TeamSelector.vue`, `components/LoginButton.vue`.
- **Suggested command:** `$impeccable adapt`

### [P1] Navigation exposes competing information architectures

- **Why it matters:** The top nav has five purposes, the sidebar adds Contribute as a sixth, the homepage actions omit Run / Operate, and the Reader Map switches to role-based routing. Long pages add a third 10+-item outline. Readers must interpret the documentation system instead of following one model.
- **Fix:** Choose one canonical top-level map, keep inactive sidebar groups collapsed, treat Contribute as secondary, and make the Reader Map reinforce rather than replace the purpose-led IA.
- **Evidence:** `docs/.vitepress/config.ts`, `docs/index.md`.
- **Suggested command:** `$impeccable distill`

### [P1] Accessibility semantics lag behind the visual structure

- **Why it matters:** The homepage renders no `main` landmark, visible current-page styling is not exposed with `aria-current`, and the task widget produces an H1→H3 jump. These gaps undermine screen-reader navigation on a surface that explicitly targets WCAG 2.2 AA.
- **Fix:** Wrap home content in one `main`, expose current-page state programmatically, and let embedded widgets inherit or configure the correct heading level.
- **Evidence:** `docs/index.md`, `docs/.vitepress/theme/index.ts`, `docs/use/tasks-and-runtime.md`, `components/RunAsMeExample.vue`.
- **Suggested command:** `$impeccable harden`

### [P2] Canonical onboarding exists, but progress is fragmented

- **Why it matters:** “Start a team pilot” has a strong three-phase narrative, then sends readers across Install, Teams, Entries, Agent Configuration, Running Agents, and First Task without a persistent completion state. The reader must remember where they were and what proves a step is done.
- **Fix:** Add a persistent pilot rail across Start pages: current step, prerequisite, completion evidence, and one next action. Keep supporting references subordinate to that path.
- **Evidence:** `docs/start/getting-started.md` and its cross-links.
- **Suggested command:** `$impeccable onboard`

### [P2] Read-only pages pay for a generic, heavy interactive shell

- **Why it matters:** Every page eagerly imports/registers interactive and auth components, starts auth behavior, and ships a production theme chunk of about 1.0MB raw / 260KB gzip. Meanwhile the visible shell still reads as themed VitePress rather than a MoltNet-specific reading system.
- **Fix:** Lazy-load page-specific widgets, initialize auth only where identity interaction is available, replace emoji with a coherent icon family, and carry restrained provenance/lifecycle cues into article components.
- **Evidence:** `docs/.vitepress/theme/index.ts`, `theme/auth/useAuth.ts`, `docs/index.md`, production build assets.
- **Suggested command:** `$impeccable optimize`

## Persona Red Flags

**Jordan (First-Timer):** Encounters “Select team” and “Log in” before understanding team context; must absorb LeGreffier, grants, Keto, runtime profiles, and daemon concepts during the first pilot; loses progress across supporting pages.

**Alex (Power User):** Benefits from search, code groups, Quick Reference, and `llms.txt`, but still scans six expanded sidebar categories plus long outlines; has no compact pilot checklist or role-filtered resume path.

**Sam (Accessibility-Dependent User):** Cannot reach the mobile hamburger at 390px; receives no home `main` landmark or programmatic current-page state; encounters a heading jump in the task widget and multiple sub-44px touch targets.

## Minor Observations

- The homepage’s fifth feature card becomes an orphan row and the dense copy makes the cards feel like a catalog rather than an entry path.
- The Reader Map is valuable but arrives after feature marketing; role-based routing may be more useful earlier.
- `docs/understand/architecture.md` is 1,249 lines and renders to roughly 26,829px at mobile width, with 40 headings and 14 Mermaid diagrams. It needs progressive disclosure or decomposition.
- The six-stage knowledge-factory ASCII pipeline clips its final “decay” stage in the content column.
- The production build passes, while the LLM-text plugin warns that the external API Reference sidebar link is normalized as an unmatched local path.

## Questions to Consider

- What if every Start page persistently answered: **Where am I, what proves this step is done, and what is next?**
- Why does Contribute compete with the canonical purpose categories instead of behaving as secondary reference material?
- Should a logged-out builder ever see “Select team” before authentication?
- If cryptographic provenance is MoltNet’s differentiator, where should that truth become visible in the article-reading experience?
